Author ProjectCards in the Workbench ¶

When to use this ¶

You edit a GMNS network in the Workbench and want the edits as a ProjectCard: a YAML file that network_wrangler applies to its own network, and that you review like code. The project_cards plugin adds this to the Workbench. Its package is netstead-project-cards, in plugins/project-cards of the netstead repository.

The plugin covers roadway changes: property changes, deletions and additions. The transit change types are listed but answer “not yet supported”.

Install and enable ¶

In the netstead workspace, uv sync --all-packages installs netstead-project-cards next to netstead. The plugin is not on PyPI yet. To add it to another environment, install it from a checkout:

uv pip install -e plugins/project-cards   # brings projectcard>=0.3.3,<0.4 and netstead[server]
uv run netstead app

An installed plugin is enabled: there is nothing to switch on. Settings → Plugins lists Project cards as loaded, with its version and the plugin API it needs (1.7). If it shows an error instead, the rest of the Workbench still runs (see Write a Workbench plugin).

Step-by-step ¶

  1. Select links. Type a request such as “Benton Street” in the Find tab’s box. Or turn on Highlight links (▯ on the map), click links or shift-drag a box over them, then press Set as selection under Highlighted links in the Find tab. A click alone only focuses a link: it never changes the selection.
  2. Pick a change. Right-click the selection (or open Selection actions ▾ in the Find tab) and choose New change ▸ Property change or New change ▸ Deletion. New change ▸ Addition adds a link, and optionally a new end node, without a selection, so it is only in the command palette (Ctrl+K, ⌘K on a Mac). The Cards dock tab opens with the form, in its Draft section.
  3. Fill in the form. The panel says what the change applies to (“1 picked link”, or “4 links matching {“name”: [“Benton Street”]}”).
    • Property change: one field per column, titled with its current value when every selected link agrees (“lanes (now 1)”), or “(values differ)” or “(empty)”. Columns that hold lists are left out. A blank field is left alone. How is set (a new value) or change (a number added to each link’s current value). When the selected links agree on a value, the card records it as existing, and If a current value differs when the card is applied says what happens when the network has moved on: error (stop, the default), warn or skip.
    • Deletion: Also delete end nodes no other link uses (clean_nodes in the card).
    • Addition: the new link’s fields, with link_id filled in with the next free id. link_id, from_node_id, to_node_id, name, facility_type, lanes and allowed_uses are required, since a ProjectCard needs them. Fill in the optional node form (it shows the next free node_id) to add an end node too. Core’s live checks flag GMNS-required link fields the addition leaves empty (such as directed), and Commit… then asks you to confirm those warnings.
    • Every form has Why (written in the card’s notes).
  4. Preview applies the change to a copy of the network, makes the copy active and shows it on the map. The network itself is untouched. The panel reads “Previewing … on …”, and Back to the network closes the copy. A second preview replaces the first. If the network changes while you preview, the panel says so: preview again to see it.
  5. Add to card applies the change to the network (never to the preview, which then closes) and lists it in the draft card. Core’s Edit tab lists it too, with project_cards as its source, and the live checks run as they do for any edit. Each change is one step: all of it applies, or none of it. Cancel closes the form and any preview. If the selection changes while a Property change or Deletion form is open, the form says it is out of date and Preview and Add to card wait until you press Reload form, which reads it again for the new selection.
  6. Watch the badge. The Cards tab shows the number of uncommitted changes with a dirty dot; its workspace tab shows the dot. The draft belongs to the network: switch networks and the panel shows that network’s draft.

  7. Commit. Under Commit, give the card a Project name, optional Tags (comma separated) and a Card file inside io.allowed_roots, then press Commit…. The dialog shows the network’s live edit warnings and the card’s YAML:

    • With no warnings, the button reads Commit.
    • With warnings, tick I have read the warnings: commit anyway, and the button reads Commit anyway. The card records the changes as they are.
    • A card that projectcard’s own validator rejects can’t be committed: the dialog says why (“Not a valid ProjectCard yet: …”).

    The file is written atomically: a failed write leaves an existing file as it was, and an existing file is replaced only when Replace an existing file is ticked. When the file is inside the open catalog’s folder, the catalog is rescanned and lists the card. A new, empty draft then starts.

Committing writes the card, not the network: the edits stay pending in the Edit tab until you save the network, as with any edit.

New card mode ¶

New card, at the top of the Draft section, walks through steps 1 to 5 as a guided mode. A step indicator reads Type → Select → Details → Add (done steps are ticked); Back returns one step and Cancel leaves the mode, closing its form and any preview.

  1. Type: Property change, Deletion or Addition. The transit types are listed, disabled: not yet supported.
  2. Select (skipped for an Addition, which needs no selection): select the facility with the shared selection. Turn on Highlight links, click links or shift-drag a box over them and press Set as selection (as in step 1), or describe them in the mode’s own box and press Select (core’s natural-language selection), or pick a saved selection and press Use saved. The mode shows a live count (“3 links selected.”); Use these 3 links opens the form. A selection that is not resolved yet (an ambiguous anchor) must be pinned in the Selection panel first.
  3. Details: the same form as step 3 above, prefilled from the selection.
  4. Add: Preview shows the change on a copy; Add to card adds it to the draft. Then Add another change starts again at Type, or Done leaves the mode; commit as in step 7.

The mode dispatches the same Actions as the right-click entry point (project_cards.preview, project_cards.add_change), so history, undo and commit work the same way.

Undo ¶

Undo last change in the panel (or Undo the draft card’s last change in the command palette) takes back the draft’s newest change, network edits included. A deletion with Also delete end nodes is two edits, and both are undone. Committed cards are not undone.

Remove, next to each change of the draft, takes out any change, not only the last. Core undoes only the network’s newest edit, so the plugin undoes the draft back to that change and applies the later changes again, in order: the network ends as if the change had never been made. A later change that depends on the removed one (a property change on a link the removed change added, or an existing value it set) no longer applies, so the removal is refused and nothing changes (“change 3 depends on the removed change 2: …”). Edit… next to a change removes it and opens its form again on the links it aimed at (selected by id, so a query selection comes back as the ids it resolved to): change the form and Add to card to put it back, at the end of the draft. Reordering changes is not supported.

Core and the plugin each undo only their own edits. Core’s Undo won’t take back a card change, and the plugin’s undo refuses when the network’s newest edit is one you made yourself: undo that one first, in the Edit tab.

Use a card catalog ¶

A catalog is a folder of existing ProjectCard files you check against the open network, preview and apply — distinct from the draft you build above.

  • Open a catalog. In the Cards tab’s Catalog section, give a folder path (inside io.allowed_roots) and press Open, or set [plugins.project_cards] catalog_dir so it opens automatically when the session starts (see the Settings reference). The folder is scanned non-recursively, plus one level of sub-folders, for .yml / .yaml / .json card files; files that are not cards are listed with why not. Refresh rescans (new, changed and removed files).
  • Does it fit? Each listed card has a status pill, and the section’s heading names the network they were checked against (“Catalog · checked against leavenworth”). A green Fits this network pill means the card applies cleanly to the network as it is now (warn and skip conflicts still fit; hover for the warning). A red Doesn’t fit pill has its first reason beside it in small text, and every reason in its tooltip: “missing link 999999”, “conflict: lanes: expected 1, found 2 on 1 of 1 links” (a property’s existing value differs and the card says existing_value_conflict: error), “already applied on leavenworth at 10:15” (with enable_apply on), or why a change can’t be applied. A gray Not checked pill has a check button beside it; the panel also checks up to 50 unchecked cards per request. A query selection with no netstead provenance reads and lists fine, but is refused when applying: “query without provenance; re-resolution not supported”.
  • Show as table (the table icon beside the folder) opens the catalog in the table pane as the read-only Cards catalog table (listed under “Plugins” in the table rail): one row per card with card_id, project, tags, change_count, change_types, fits, reason, links_targeted and modified. Sort it by any column and filter it with the column funnels (any of on tags picks the cards with a tag); clicking a row brings the Cards tab forward with that card marked. The table follows the catalog: a rescan, a check or a file action reads it again.
  • Preview shows every change of the card on a copy of the network (as in step 4 above) and highlights the links and nodes it targets on the map, so you can see what it touches before committing to it.
  • Apply… (only when [plugins.project_cards] enable_apply = true; it is off by default, and project_cards.apply_card is refused while it is) applies the card to the network, all or nothing, through the same path as a draft change — no file is written, since the card already exists. Its dialog offers If a current value differs when the card is applied (existing_value_conflict: error / warn / skip) and, for a card that doesn’t fit, ignore missing ids: with it checked, a missing id is skipped and listed instead of refusing the whole card.
  • This session lists what this session did with cards, newest first, each with an icon, a verb and the time: Saved for a draft committed to a file, Renamed, Duplicated, Deleted, Restored and Edited the metadata of for the catalog file actions, and Applied to when enable_apply is on. Saving a card does not apply it to anything: its changes were already on the network as the draft.
  • Session summary builds a plain-text summary (network, source, spec version; the applied cards with their edit ids; the draft, if any; and this plugin’s actions in order, each ok or failed) with Copy and Download buttons. GET /api/plugins/project_cards/summary.txt serves the same text.

Edit a card ¶

Edit, on a catalog card, loads it into the open network’s draft: every change of the card is applied, as Import does (all or nothing), and the draft takes the card’s project, tags, dependencies and notes. The draft remembers the card’s file (“Editing main.yml (…)”) and the commit fields are filled in with the card’s. Then edit the draft: Remove or Edit… its changes, or add new ones (see Undo).

  • If the draft already has uncommitted changes, Edit asks first: Replace the draft undoes them (network edits included) and loads the card instead.
  • Edit applies the card to the network, so it needs a network the card applies to (a Fits this network pill). A card committed in this session is already on its network: reopen the network (or open another copy) to edit it.
  • Commit… then offers Save over main.yml (replace the card’s file) or Save as new file (the Card file field, which must name another file; an existing one is replaced only with Replace an existing file). The catalog is rescanned after either.

From Python: project_cards.edit_card(card_id, replace_draft=False) and project_cards.remove_change(index).

Manage the catalog’s files ¶

Each catalog card’s row of icon buttons (hover one for its name) ends with four file actions; Details shows the card’s path. Each one is a recorded Action, listed in the session summary under Catalog files; the catalog is rescanned after it. They change files, not the network, and the assistant is not offered them.

  • Rename… gives the file a new name in the catalog folder (or sub/name.yml, one sub-folder down). A name without a suffix keeps the card’s. An existing file with other content is replaced only when Replace an existing file is ticked.
  • Duplicate copies the file, byte for byte, to <name>-copy.yml (-copy-2, … when that is taken).
  • Edit metadata… changes the card’s project name, tags and dependencies (prerequisites, corequisites, conflicts; comma separated). Only those keys of the file change; its changes and notes stay as they are, though YAML comments are not kept.
  • Delete moves the file to a .trash folder inside the catalog folder; nothing is deleted for good. The status line offers Undo delete, which moves it back (project_cards.restore_card). Empty .trash yourself when you are sure.

Every new or rewritten file stays inside io.allowed_roots and the catalog folder (nothing hidden, at most one sub-folder down), and the card is validated with projectcard before it is written: a card projectcard rejects is not renamed, copied or rewritten.

Inspect a card ¶

Inspect, on a catalog card or under the draft, opens a read-only view of the card:

  • its Project, Tags, Dependencies (prerequisites, corequisites, conflicts), Notes and File;
  • each change, numbered, with its type, its facility (“links 1, 2”, or links matching {"name":["Benton Street"]} with the number of links it resolved to), its property changes as existing → new (“lanes: 1 → 2”, “lanes: 1 → change by +1”) and whether it applies to the open network (“Applies: 2 records found”, “0 found; missing 999999”, or the reason it can’t be applied). The draft’s changes are already on its network: “In the draft: applied to …”.

Click a change to highlight its links on the map. The map does not zoom to them: the Workbench gives plugins no camera control yet, so pan to them yourself (or use Find to zoom to a link). YAML shows the card’s text: the file itself for a catalog card, the YAML a commit would write for the draft. Close clears the highlights. Inspecting changes nothing; GET /api/plugins/project_cards/card?card_id=<id> (or ?draft=true) serves the same view as JSON.

From Python: project_cards.open_catalog(path), project_cards.refresh_catalog(), project_cards.check_card (card_id), project_cards.preview_card(card_id), project_cards.apply_card(card_id, existing_value_conflict= ..., ignore_missing=...) and project_cards.session_summary() — see From Python below for the Action names. Needs Host API 1.7 (host.readable, host.list_dir, host.history).

Import a card ¶

Under Import a card, give the path of a card or edit log, then press Import. The path must be inside io.allowed_roots. Every change in the file is applied to the network and added to the draft, all or nothing: if one fails, none are applied, and the message names the one that failed (“change 2 of 2: …”). An empty draft takes the card’s project, tags, dependencies and notes.

Import reads YAML and JSON cards. The edit log that the offline validation report’s “Fix locally” editor downloads (see Triage and fix findings) is one: each fix is a picked id with ignore_missing: false, and its netstead.note[<i>] line becomes the change’s note. Edit logs written before netstead 2026-10-20 are not schema-valid (the facility holds model_link_id at the top level, and each change carries its own notes); import still reads them, and each of those notes becomes the change’s note, written into the card’s notes on commit.

Import refuses:

  • Scoped (time-of-day) values, in an added record or as a scoped property change.
  • TOML cards: projectcard 0.3.3 can’t read them. Use YAML or JSON.
  • Transit changes, pycode and roadway_managed_lanes.
  • A query selection without netstead provenance. A card that selects links by a query (name, ref, …) is applied to the link ids recorded in its notes, so only cards that the plugin wrote can be imported this way. One with no provenance reads fine (it is an unresolved selection), but import and apply refuse the change: “query without provenance; re-resolution not supported”. Re-resolving a query on another version of the network is planned for later.
  • A deletion that doesn’t select by id (model_link_id / model_node_id).

What goes in the card ¶

The card uses network_wrangler’s names. GMNS names map to them through a data file, netstead_project_cards/mappings/gmns_to_wrangler.yaml (link_id → model_link_id, from_node_id → A, to_node_id → B, facility_type → roadway). A column it doesn’t list keeps its GMNS name.

You did The card says
Picked links (click or box), as a Link list in GMNS ids facility: {links: {model_link_id: [...], ignore_missing: false}}
Selected by a request (“Pine Street between Orchard Street and Central Avenue”), as a Segment facility: {links: {name: [Pine Street], ignore_missing: true}, from: {model_node_id: 33}, to: {model_node_id: 19}}, plus a netstead.resolved[<i>] line in the card’s notes
Either, in OpenStreetMap ids facility: {links: {osm_link_id: ['5846369'], ignore_missing: false}} (Link list), or the Segment with from: {osm_node_id: '46999094'} and to: {osm_node_id: '46993874'}
Deleted links roadway_deletion by id: ignore_missing: false for picked links, the query’s own flag for links a request selected; Also delete end nodes is clean_nodes: true
Added a link roadway_addition in network_wrangler’s names, with walk_access, bike_access and drive_access derived from allowed_uses
Wrote a note a netstead.note[<i>] line in the card’s notes

Segment or Link list, and the id system ¶

A change’s facility is written in exactly one of two forms, never a mix, chosen in the change form (and by the facility_form and id_system fields of project_cards.add_change and project_cards.preview). The two choices are the Find tab’s, with the same ID system choice:

  • Segment: the facility by name or ref with the from and to nodes. A re-import can find it again on another version of the network. It is the default for a selection made by a request that names a facility, and it is disabled, with the reason as its tooltip, for a click or box selection, which has no name (“This selection has no named segment; use Link list”).
  • Link list: only ids. It is the default for clicked or box-selected links.

The ID system is GMNS (model_link_id, model_node_id, the default) or OpenStreetMap (osm_link_id, osm_node_id, written as text as ProjectCard has them). OpenStreetMap needs the network’s osm_way_id and osm_node_id columns, and a selected link with no OSM id refuses it. One OSM way can be split into several links, so a Link list in OSM ids applies to every link of those ways, not only the selected ones: the form says so (“OSM way 5846369 also covers 11 links outside this selection”) and the change applies to all of them. Overture GERS is disabled with the reason “ProjectCard has no key for GERS ids”; asking for it from Python is refused the same way. A deletion takes GMNS link ids only.

The draft and the Inspect view say which was used, per change: Segment: Pine Street, node 33 → 19 (GMNS), Link list: 1 OSM way (OpenStreetMap).

On import and in the catalog’s fit check an OSM Link list is resolved on the open network, osm_link_id against the link table’s osm_way_id (all links that carry it) and osm_node_id against the node table’s: an id the network lacks is listed as missing (OSM way 999) and refuses the card unless ignore_missing is true. A Segment is applied to the links its provenance line recorded.

Provenance notes ¶

A ProjectCard change has no field for extra information, so the plugin keeps it in the card’s top-level notes, one line per item, numbered by the change’s position (from 0):

notes: |-
  Ski season fixes
  netstead.note[0]: issue 42: two lanes
  netstead.resolved[1]: model_link_id=[1, 5, 6, 8]
  • netstead.resolved[<i>]: model_link_id=[...] records the links that Segment i matched when you made the change (in GMNS ids, even when the Segment names its nodes in OpenStreetMap ids). Import applies the Segment to these ids. A Link list needs no such line.
  • netstead.note[<i>]: … is change i’s Why, on one line.

The rest of the notes are yours: the commit’s notes field, from Python or the assistant. Import reads the provenance lines back and keeps the other lines as the card’s notes.

ignore_missing ¶

ignore_missing says what network_wrangler does when a selected record is not in the network: fail (false) or skip it (true).

  • Picked links are written by id with ignore_missing: false. A fix aimed at specific links should fail loudly when one of them is gone.
  • A query selection keeps the query’s own ignore_missing, which is true (network_wrangler’s default) when the query has none. The plugin applies it now too: a resolved id the network no longer has is skipped and listed, instead of refusing the change.
  • Deletions are written by id (the links the selection resolved to). Picked links get ignore_missing: false; links a query selected keep the query’s flag, so with true a resolved link that is gone is skipped and listed, as for a property change. A deletion’s nodes always get false.
  • Reading a card, a selector without ignore_missing reads as true. A deletion keeps its links’ flag; its nodes’ flag is dropped and written back as false. The offline edit log’s ids read as false.

From Python ¶

Each step is a recorded Action in the session history, so Copy as Python in the history strip replays it. The copied lines import from netstead_project_cards.actions:

Action What it does
project_cards.add_change (AddChange) Apply one change and add it to the network’s draft.
project_cards.undo_change (UndoChange) Undo the draft’s last change.
project_cards.remove_change (RemoveChange) Remove any change of the draft (the later ones are re-applied).
project_cards.preview (PreviewChange) Preview a change on a copy of the network.
project_cards.close_preview (ClosePreview) Close the preview.
project_cards.commit (CommitCard) Write the draft as a card file and start a new draft.
project_cards.import (ImportCard) Apply a card or edit log to the draft, all or nothing.
project_cards.edit_card (EditCard) Load a catalog card into the draft to edit it, remembering its file.
project_cards.open_catalog (OpenCatalog) Open a folder of card files as the catalog.
project_cards.refresh_catalog (RefreshCatalog) Rescan the open catalog’s folder.
project_cards.check_card (CheckCard) Check whether a catalog card applies to the network now, without changing anything.
project_cards.preview_card (PreviewCard) Preview a catalog card’s changes on a copy of the network.
project_cards.apply_card (ApplyCard) Apply a catalog card to the network, all or nothing; record it as applied.
project_cards.rename_card (RenameCard) Rename a catalog card’s file.
project_cards.duplicate_card (DuplicateCard) Copy a catalog card to <name>-copy.yml (or a name you give).
project_cards.delete_card (DeleteCard) Move a catalog card’s file to the catalog’s .trash folder.
project_cards.restore_card (RestoreCard) Move a deleted card back from .trash.
project_cards.update_card_meta (UpdateCardMeta) Change a catalog card’s project, tags and dependencies.
project_cards.session_summary (SessionSummary) The session summary as plain text.

session.dispatch (or its alias app.do) runs them. A change targets the shared selection (use_selection=True), a saved selection (saved_selection="<name>", Python and the assistant only), or names its own facility. This example opens the Leavenworth fixture, sets link 1 to two lanes, undoes a second change and commits the card to a temporary folder. plugins=[plugin()] installs just this plugin; a Session() without it loads every installed plugin, as netstead app does:

import tempfile
from pathlib import Path

from netstead.fixtures import leavenworth
from netstead.workbench import OpenNetwork, Select, Session
from netstead_project_cards import plugin
from netstead_project_cards.actions import AddChange, CommitCard, UndoChange
from netstead_project_cards.types import PropertyChange, RoadwayPropertyChange

fixture, out = leavenworth.parquet_dir(), Path(tempfile.mkdtemp())
roots = {"io.allowed_roots": [str(out), str(fixture.parent)]}
app = Session(project_dir=out, overrides=roots, plugins=[plugin()])
app.dispatch(OpenNetwork(source=str(fixture)))
app.dispatch(Select(link_ids=[1]))
lanes = RoadwayPropertyChange(property_changes={"lanes": PropertyChange(existing=1, set=2)}, note="issue 42")
app.dispatch(AddChange(use_selection=True, change=lanes))
app.dispatch(AddChange(use_selection=True, change={"type": "roadway_property_change",
                                                   "property_changes": {"free_speed": {"change": -5}}}))
app.dispatch(UndoChange())  # takes back the free_speed change
result = app.dispatch(CommitCard(path=str(out / "link-1-lanes.yml"), project="Link 1 lanes", confirm_warnings=True))
print(result["card_id"], result["changes"])  # link-1-lanes 1

A change can be a model, as for lanes, or a plain dict, as in the copied lines. confirm_warnings=True stands in for the dialog’s confirmation: without it, a network with live edit warnings refuses the commit. The written file loads with projectcard’s own reader:

import projectcard

print(projectcard.read_card(out / "link-1-lanes.yml", validate=True).project)  # Link 1 lanes

Selecting by a request needs a language model (see Explore in the Workbench). Preview and import work the same way:

from netstead_project_cards.actions import ClosePreview, ImportCard, PreviewChange

app.dispatch(Select(utterance="Benton Street"))
app.dispatch(PreviewChange(use_selection=True, change={"type": "roadway_deletion"}))
app.dispatch(ClosePreview())
app.dispatch(ImportCard(path="cards/edit-log.yaml"))

Over HTTP, POST /api/actions takes the same Actions as JSON ({"type": "project_cards.add_change", ...}). The panel also reads routes: GET /api/plugins/project_cards/form (the form for a change type on the selection), GET /api/plugins/project_cards/commit-check (the warnings, problems and YAML the commit dialog shows), /catalog (the open catalog), /card (the Inspect view) and /summary.txt. All only read.

The library behind the Actions is usable on its own: DraftCard builds a card from the change model and writes it with to_yaml(), read_card_file reads one back, and netstead_project_cards.validate.card_problems runs projectcard’s validator.

With the assistant ¶

The assistant offers a plugin’s Actions only when you opt in. In Settings → Assistant: actions & plugins, or in ~/.config/netstead/config.toml:

[assistant]
plugins = ["project_cards"]

plugins is the opt-in. With a model on this machine (Ollama), the default compact_tools = "auto" gives it a smaller set of tools. That set includes adding, undoing and previewing a change and closing the preview, but not committing or importing, which need a file path. To draft those with a local model as well, set compact_tools = "off".

Every project_cards Action changes a network, opens or closes a preview, or writes a file, so the assistant drafts each one for you to approve. Nothing runs until you do. A drafted change made while a preview was open is refused as stale if the previewed network has changed since.

Pitfalls ¶

  • Roadway only. Transit change types answer “not yet supported” in the palette, the Actions and the assistant. roadway_managed_lanes and pycode are not supported either.
  • One number or text per property. A card can’t set a property to empty (clear a cell with a core edit instead) or to a list. true / false are written as 1 / 0. Scoped (time-of-day) values are not supported.
  • A change must be a valid ProjectCard before it is applied. For example, a request that names both a street and a route number gives a query that ProjectCard doesn’t allow, so Add to card refuses it: select by one of them.
  • An added record’s fields must be columns the network has. A field with no column answers “not yet supported”.
  • A draft lives in the Workbench session. Closing the network or the app drops its draft. The network’s edits stay pending until you save or discard them. Commit to keep the card.
  • A change that applies nothing is refused, for example a query whose links are all gone with ignore_missing: true, or every property skipped by skip.
  • Importing a query needs provenance. See Import a card.
  • The panel works on the shared selection. To use a saved selection, select it first, or use saved_selection from Python or the assistant.
  • A committed card’s id is not written to the network’s lineage. It is listed in the plugin’s state (plugins.project_cards.committed) for the session.
